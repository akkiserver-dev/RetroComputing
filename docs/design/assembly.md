# アセンブリ仕様（策定中）

更新日: 2026-10-26（JST）

この文書は、アセンブリに関する質問への回答を整理した仕様の途中経過である。
確定事項、仮設定、未決事項を区別し、質問への回答に応じて更新する。
専用APIやゲーム内ブロックの実装が完了したことを示す文書ではない。

## 1. 仕様の根拠と対象

- 仕様は今回の対話におけるユーザーの回答から決める。
- 過去の引き継ぎ資料は古いため、そこにある仕様を現在の決定として採用しない。
- 組み立て対象は基本的にほぼすべてのハードウェアを想定する。ただし、具体的な対象一覧と例外は未定。
- ティアは導入せず、アセンブリを構成する部品によって性能や対応機能を変える。
- 完成品の用途は一種類に限定する。CPUと描画、描画と通信など、複数用途を一枚の基板に同居させる構成は採用しない。

## 2. 部品の製造と組み立て

工程は次のように分ける。

1. 抵抗、コンデンサ、トランジスタなどの電子部品を、クラフトや工業機械で加工する。
2. 描画チップ、RAMチップなど、機能を持つ部品を製造する。
3. アセンブラで機能部品を基板上に配置し、完成品を組み立てる。

アセンブラで主に扱うのは機能部品である。
電子部品の具体的な種類、加工レシピ、工業機械の仕様は未定。

基本的なプレイでは、特定のレシピから完成品を入手できるようにする。
すべてを部品から自由に設計・製作する工程は、構成を自由に作り込みたいプレイヤー向けにも提供する。

組み立て済みの完成品を、一つの部品として別のアセンブリに組み込める。
部品としての占有形状は、完成品のコンポーネントの種類によって定義する。
内部の基板サイズをそのまま部品の占有サイズにすることは要求しない。
用途の適合条件、内部構成の扱い、既定レシピの完成品の内部構成は未定。

## 3. PCBと製作対象

- 基板アイテムは共通のPCBのみを用意する。
- プレイヤーはアセンブラで製作対象を選択し、その対象について部品を配置して設計する。
- 基板のサイズは製作対象ごとに固定する。
- 同じ製作対象について、プレイヤーが基板の縦横サイズを変更する方式は採用しない。
- 製作対象ごとの具体的な基板サイズは未定。

途中で検討した「専用基板と汎用基板を別々のアイテムとして用意する」案は、
共通PCBとアセンブラでの製作対象選択に訂正された。

## 4. 部品の配置

### 4.1 配置領域と形状

- マス目を使って部品を配置する。
- 部品は90度ずつ回転できる。
- 部品の占有形状は長方形に限定しない。L字など、長方形以外の形にも対応する。
- 配線は自動で処理し、プレイヤーによる配線操作は要求しない。
- ボードのサイズと部品の占有形状に応じて、部品が収まる配置を考えるゲームプレイにする。

この方針から、配置判定には各部品の占有マスと回転後の形状を用い、
基板外へのはみ出しや占有マス同士の重なりを検出する必要がある。
形状の具体的なデータ形式、回転の基準点、反転の扱いは未定。

### 4.2 配置と性能の関係

- 同じ部品の組み合わせであれば、基板上の配置が変わっても性能は同じ。
- 配置はスペースの使い方に影響する。
- 部品同士の距離や隣接関係による性能補正は設けない。

## 5. 構成条件と互換性

- CPUやビデオカードの主要チップは一個とし、補助部品やメモリを追加して構成する。
- 必須部品の不足や不適合がある構成は組み立てられない。
- 不足や不適合はアセンブラの画面に表示する。
- 互換性は、例えば「描画チップにRAMチップを組み合わせられる」といった部品の種類によって定義する。
- 細かなメモリ規格や接続規格の照合、部品モデルごとの対応一覧を基本仕様とすることは決めていない。

製作対象ごとの必須部品、補助部品の搭載数制限、部品の分類体系、
CPUやビデオカード以外の対象における主要部品の扱いは、今後具体化する。

## 6. 性能と対応機能

- 性能と対応機能は搭載部品によって決まる。
- 補助部品は、容量や速度に加えて、対応機能も追加できる。
- 例えば、ビデオカードの対応する描画命令や画像形式を補助部品で拡張できる。

通常のパーツには個体差を付けず、パーツの種類ごとに性能を定義する。
例外として、CPUダイなどの製造されるコンポーネントは性能を分けられる。
ダイの性能差は設計内容によって生じる。
材料・レシピ・加工条件などの製造方法による性能差は付けない。
以前の「製造方法によって性能を変える」という案は、この方針に訂正された。
例外とするコンポーネントの具体的な対象範囲は未定。

### 6.1 ビデオカードのRAM容量

- RAMチップは複数搭載でき、容量を合計する。
- 基板に収まる分だけRAM容量を増やせる。
- 描画チップ側に、扱えるRAM容量の独自上限は設けない。

速度や対応機能など、容量以外の性能をどのように合成するかは未定。
サーバー全体の資源制限や通信制限は、部品由来の性能とは別に扱う。

### 6.2 ダイの設計

シリコン上に要素を配置してダイを設計できるようにする。
配置する要素は、演算器・キャッシュ・制御回路などの機能ブロック単位とする。
論理ゲートや個々のトランジスタを配置する粒度は採用しない。

- 基板とダイには共通の設計・配置システムを使い、基板とシリコンの見た目はテクスチャで切り替える。
- ダイでも、同じブロック構成であれば配置場所による性能差は付けない。
- ダイの性能は機能ブロックの構成から決まり、製造方法では変わらない。
- ダイ設計では仮想の機能ブロックを配置して設計図を作成する。
- 製造機械が、材料と設計図から実物のダイを製造する。

基板の組み立てでは実物部品を配置し、ダイ設計では仮想ブロックを配置するという工程の違いを、
共通の配置システム上で扱えるようにする。
ブロック構成を使った具体的な性能の計算方法、製造機械の詳細は未定。

## 7. 組み立てと完成品

- 設計画面には実物の部品アイテムを配置し、その構成を組み立てる。
- 完成後の部品交換、組み直し、分解はできない。

### 7.1 仮設定

初期実装では、組み立ては即座に完了し、時間と電力を消費しない。
これは仮設定であり、将来の時間・電力消費を否定する決定ではない。

PCBや部品の具体的な消費方法、組み立て開始前の操作、
アセンブラの破壊やインベントリ操作に伴うアイテムの取り扱いは未定。

## 8. 設計図

- 設計図アイテムに設計を保存できる。
- 設計図は別のアセンブラでも使用でき、同じ構成を繰り返し製作できる。
- 設計図には部品の種類、数量、配置を記録し、同じ種類の部品を使って再現する。
- 「RAMチップなら別の種類でもよい」といった部品の役割だけによる代用は行わない。
- CPUダイなど、設計内容によって性能が違う部品も、部品の種類が同じなら使用できる。
- 使用部品の設計内容や製造条件まで一致することは要求しない。

回転は配置情報の一部として再現できる必要がある。
設計図の複製、材料の供給元、
設計図を適用したときの部品配置操作は未定。

## 9. 定義の追加と更新

### 9.1 追加API

- 新しい部品や製作対象は、JavaのアドオンMODから追加できればよい。
- データパックからの部品・製作対象の追加や変更は、今回の要求に含めない。
- 具体的なAPIの型名、メソッド、登録時期、登録方法は未確定。

### 9.2 製作済み完成品の更新

- 部品の性能が更新された場合、完成品の性能を搭載部品の最新定義から再計算する。
- 製作時の性能を固定して使い続ける方式は採用しない。
- 配置や組み立ての成立条件は、製作時に判定する。
- 更新後の部品形状や必要部品の条件に既存の構成が合わなくても、部品自体が存在する限り、既存品は性能を再計算して使い続けられる。

既存品の継続使用と、新たな製作は区別する。
設計図を使って新たに製作する場合も、その時点の配置・構成条件を満たす必要がある。

部品や製作対象そのものが削除された場合の扱い、
再計算するタイミング、保存形式と移行方法は未定。

## 10. API設計に必要な責務（設計途中）

以下は、確定したゲームプレイを実装するために整理が必要な責務である。
公開APIの具体的な形を決定したものではない。

| 責務 | 扱う情報や処理 |
| --- | --- |
| 製作対象の定義 | 完成品の用途、固定の基板サイズ、必要な部品と構成条件 |
| 部品の定義 | 部品の種類、占有形状、役割、性能と対応機能への寄与 |
| 配置情報 | 使用部品、個数、位置、90度単位の回転 |
| 配置検査 | 基板内に収まるか、占有マスが重ならないか |
| 構成検査 | 主要チップ数、必須部品、不足や不適合の診断 |
| 性能計算 | 搭載部品の最新定義から完成品の性能・対応機能を算出する処理 |
| 設計図 | 部品の種類・数量・配置の保存と再現 |
| 完成品の保存 | 最新定義による再計算に必要な搭載部品情報の保持 |
| ゲーム側との接続 | 部品アイテム、PCB、アセンブラ画面、完成品アイテムやブロックとの対応 |

### 10.1 検証UIと本番GUI

- 本番GUIはユーザー自身が作成する。
- この作業でGUIが必要になった場合は、動作確認に必要な仮配置に留める。
- 共通の設計・配置処理を、本番GUIの見た目やレイアウトから切り離して扱う。

## 12. Screenとの関係

今回の対話で示された、後続のScreen実装に関する方向性を記録する。
アセンブリ仕様とAPIを先に整理するため、Screenの実装作業は保留している。

- ブロック名は「Screen」とする。
- CC:TやOCCEのようなマルチブロック画面を想定する。
- 解像度の最大は640×480、色深度の最大は16bitとする方向で合意している。
- TEXTモードとBITMAPモードを維持する。
- ティアではなくアセンブリによって性能を変える。
- 検証用には、最高性能で各モードを自由に試せるグラフィックテストスクリーンを作る。
- テスト用ブロックはTEXT・BITMAPのさまざまな描画を行うものであり、後の本実装でも使える基礎を作る。
- 当面の実装対象はMinecraft 1.21.1。
- マルチプレイの通信上限は固定値を確定せず、接続時の通信能力確認と接続状況に応じた変動を検討する。
- 対話中に提示された帯域の数値は検討例であり、確定値として採用しない。

マルチブロックの結合規則、描画・通信方式の具体的な実装、
性能の計測方法と上限調整アルゴリズムは未確定。
